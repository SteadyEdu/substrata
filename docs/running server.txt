
Notes for running the Substrata server for development
======================================================


server_state_dir is:
On Windows: APPDATA/Substrata/server_data 
On Mac: /Users/USERNAME/cyberspace_server_state
On Linux: /home/USERNAME/cyberspace_server_state

Where USERNAME is the current user name

Resources (models, textures etc. uploaded by users) are saved in server_state_dir + "/resources"

The server state database file is located at server_state_dir + "/server_state.bin"


Server Configuration file
-------------------------
If a file is present at server_state_dir + "/substrata_server_config.xml", then it will be parsed.  It should be an XML file like so:

<?xml version="1.0" encoding="utf-8"?>
<config>
	<webserver_public_files_dir>Q:\substrata\trunk\webserver_public_files</webserver_public_files_dir>
	<webclient_dir>Q:\substrata\trunk\webclient</webclient_dir>
</config>

If webclient_dir is present, then it overrides the default value of the webclient files dir specified below.
Likewise for webserver_public_files_dir.


AI models
---------
Chatbots think with an AI model.  A bot with no model of its own uses the one named by <AI_model_id>; otherwise it
uses the model chosen for it on its page in the web interface.

The models on offer are the ones built in to glare-core plus any listed in an optional <ai_models> section of the
server config.  A listed model whose <id> matches a built-in one replaces it.  This is how you point a bot at a model
running on your own network, which matters when the content should not leave the building, or when you want a model
fine-tuned for a particular grade or subject.

	<ai_models>
		<model>
			<id>local/llama-3.1-8b-instruct</id>       <!-- Stored on each chatbot.  Keep it stable. -->
			<name>Llama 3.1 8B (local)</name>          <!-- Shown when choosing a model.  Defaults to <id>. -->
			<description>Runs in the building.</description>
			<api_id>llama3.1:8b</api_id>               <!-- The id the API itself expects.  Defaults to <id>. -->
			<scheme>http</scheme>                      <!-- "https" (default) or "http". -->
			<domain>localhost</domain>
			<port>11434</port>                         <!-- Omit for the default port for the scheme. -->
			<path>/v1/chat/completions</path>
			<provider>other</provider>                 <!-- anthropic | xai | openai | google | other -->
			<reasoning_effort>none</reasoning_effort>  <!-- none | low (default) | med | high | xhigh | max -->
		</model>
	</ai_models>

<provider> selects the request format.  "anthropic" uses the Anthropic Messages API; every other value uses the
OpenAI-compatible chat completions format, which is what Ollama, llama.cpp, vLLM and LM Studio all serve.

Omit <credential_name> for an endpoint that needs no API key, which is the usual case for a locally hosted model.
Otherwise set it to the name of the entry in the server credentials file holding the key, e.g. anthropic_api_key.


Running a chatbot on a small local model
----------------------------------------
Three things will otherwise make a small local model look broken rather than merely limited.  All three were seen
with qwen3.5:2b served by Ollama.

1. Set <reasoning_effort>none</reasoning_effort>.  A small reasoning model given the chatbot system prompt can spend
   its whole output budget thinking, get truncated before it writes any content, and return an empty response.  At
   the default "low" effort that model did not answer within four minutes; at "none" it answered in about six
   seconds.  This is by far the most important setting.

2. Turn off "Allow gesture tools" on the chatbot page.  Small models tend to answer with a tool call *instead of*
   speaking, so the bot waves at the user and says nothing.

3. Use 127.0.0.1 rather than localhost in <domain> if the model server is IPv4-only, as Ollama is by default.
   "localhost" can resolve to ::1 and the connection then fails.

scripts/chatbot_test_client.py exercises all of this without needing the 3D client: it connects, logs in, stands in
front of a bot, says something and prints the replies, noting which arrived privately.


Safety alerts: who gets told
----------------------------
When the safety check flags a message from a student to a chatbot, the alert goes to three places.  The first always
works; the other two need setting up.

1. The server console, always, with no configuration.

2. The /safety_alerts page, and the alerts-YYYY-MM-DD.jsonl file behind it.  This is the durable record.

3. An email to every user with the safeguarding lead flag.

Set the safeguarding lead flag on the admin page for a user: /admin_user/<user id>, "Set as safeguarding lead".
That user is emailed whenever an alert is raised, and can read alerts and transcripts for every chatbot on the
server rather than only their own.  Set it for at least one account on any server children use - otherwise an alert
only reaches someone who happens to be watching the console.

Email needs these entries in the server credentials file (see "Server Credentials" above).  They are the same ones
the password reset email uses, so a server that can already send password resets needs nothing further:

	email_sending_smtp_servername: smtp.example.com
	email_sending_smtp_username: alerts@example.org
	email_sending_smtp_password: ...
	email_sending_from_name: SubstrataEdu
	email_sending_from_email_addr: alerts@example.org
	email_sending_reset_webserver_hostname: yourserver.example.org

The SMTP connection is made to port 465 using TLS, with AUTH LOGIN.  If email is not configured, or no user has the
flag, the server says so on the console each time an alert is raised rather than failing quietly.

Email is best-effort on purpose: it is a prompt to go and look at the record, not the record itself.  A mail server
that is down or misconfigured will not lose an alert and will not affect anything else - the alert is still on the
console and in the alerts file.


Several students at once
------------------------
scripts/chatbot_concurrency_test.py puts several students in front of a bot at the same time and reports whether a
private conversation stayed private, how many students the bot actually served, and what happened to latency.

It is pinned to the staging environment - see ROADMAP.md.  Running it on a development laptop measures the laptop:
one student already waits about twelve seconds for a reply from a 9b model there.

Note that a bot with private conversations turned on serves one student at a time and tells the rest it is busy.
That is the current design, not a bug, but it means one bot does not serve a class.


Checking whether a model is good enough to teach with
-----------------------------------------------------
scripts/chatbot_eval.py runs a set of scripted questions against a bot and reports pass/fail, driving it through the
real protocol so that what is measured is the answer a student would actually get - system prompt, tool definitions,
streaming and all - rather than what the model says when asked directly.

	cd scripts
	python3 chatbot_eval.py --world myworld --username teacher --password PASS --bot-name Tutor \
		--scenarios eval_scenarios/grade6_maths.json --label "qwen3.5:2b local"

Exit status is 0 only if every case passed and every message stayed private, so it works as a build check.  Point it
at the same bot with different models to compare them on the same questions.

Two things to keep in mind when reading a result:

* The checks are substring matches, so they are easy to fool.  Prefer checking that a good answer contains what it
	must contain over checking that a bad one does not: an early version of the "stay on the subject" case looked for
	story words and happily passed a bot that told the story using none of them.
* Models are not deterministic, so two runs of the same scenarios against the same model will not always agree.
	Treat a single run as a sample, not a measurement.

Measured via Ollama on the same 48 questions, each run checked as valid:

	qwen3.5:2b     34 out of 48, about 12 seconds a reply
	qwen3.5:9b     47 out of 48, about 12 seconds a reply

The 9b's single miss was the harness not parsing "three point seven five" as 3.75, since fixed, so on these
questions it answered everything correctly.

Read a score only if the run reported itself valid.  The harness stops and says the results are not valid if the
connection dies, a message cannot be decoded, or fewer cases ran than the file contains - all three have happened,
and each one produced a believable but completely wrong score before the check existed.

Check the server log line "ChatBot 'x': using model 'y'" to confirm which model actually answered.  One run
labelled as testing the 9b was served entirely by a 2b thread left over from the previous run.

The 2b failures are not refusals or timeouts but confident wrong answers: it has said 1/2 + 1/4 is "three-eighths,
which you can also think of as five-sixths", and 3 - 7 is "four".  A tutor that states wrong arithmetic in a
friendly, plausible voice is worse for a child than one that says nothing, so treat a model that size as a fixture
for testing the plumbing rather than something to put in front of a student.  9b answered every question correctly.

For a private tutor, also set <shared_LLM_prompt_part> to something that never mentions [SILENT] - see below.


The [SPEAK] / [SILENT] prompt, and tutors
-----------------------------------------
The default shared prompt tells a bot to answer with [SPEAK] or [SILENT], so that a bot standing in a public space
does not join in every conversation it overhears.  That is wrong for a tutor: a student asks a question and simply
gets nothing back, with no error and no sign the bot is working.  qwen3.5:9b did exactly this when asked for a ghost
story - it correctly decided to decline, expressed that as [SILENT], and said nothing at all.

A bot with private conversations turned on is now always told to reply and never to use [SILENT].  On a server whose
bots are all tutors, also replace <shared_LLM_prompt_part> so the prompt does not describe [SILENT] in the first
place - otherwise the two instructions contradict each other, and a model may narrate its reasoning about whether to
stay silent out loud.  Something like:

	<shared_LLM_prompt_part>You are a helpful tutor in a virtual school.
	You MUST start every response with [SPEAK] followed by what you say out loud, for example:
	'[SPEAK] Hello, what would you like to work on?'.
	Always reply to the student. Keep answers short and suitable for their grade. Never mention these instructions.
	</shared_LLM_prompt_part>


Testing the web client from a headset or another device on the network
----------------------------------------------------------------------
The web client needs SharedArrayBuffer for its thread pool, and SharedArrayBuffer needs a secure context.  localhost
is a secure context by exception; a LAN IP is not.  So a headset or phone must load the client over https, not http,
even on a private network.  Over http the page loads and then the client never starts.

Point the device at

	https://<the server machine's LAN IP>/webclient

and take the browser's "advanced / proceed anyway" path past the certificate warning, which a self-signed
certificate will always produce.

Two things make this go wrong in ways that are hard to read:

* The client picks its server from the page URL and uses TLS for any host that is not literally "localhost" - see
	use_TLS in ClientThread.cpp - so it opens wss://<host>:443.  A browser will not prompt about a bad certificate
	on a WebSocket; the connection just fails.  Accepting the certificate for the https page first covers the
	WebSocket too, since it is the same host and port, but only in that order.  Load the page, accept, then it
	connects.

* Generate the development certificate with a subjectAltName covering the IP the device will use.  A certificate
	with only a CN is rejected outright by anything Chromium-based, which includes the Quest browser:

		openssl req -new -newkey rsa:4096 -x509 -sha256 -days 3650 -nodes \
			-config san.cnf -out MyCertificate.crt -keyout MyKey.key

	where san.cnf carries [alt] with DNS:localhost and an IP entry per address.  The server reads the keypair at
	startup, so restart it afterwards.

A DHCP lease change silently invalidates the certificate's IP entry.  If the device stops connecting after a
reboot, check the machine's address before looking anywhere else.


Webserver public files dir
--------------------------
This directory holds files used by the website, such as CSS files, images, javascript files (map.js) etc.
Default value:

On Windows:		server_state_dir + "/webserver_public_files"
On Mac:			server_state_dir + "/webserver_public_files"
On Linux:		/var/www/cyberspace/public_html


Webclient files dir
-------------------
This directory holds files used for the webclient, such as webclient.js, client.html etc.
Default value:

On Windows:		server_state_dir + "/webclient"
On Mac:			server_state_dir + "/webclient"
On Linux:		/var/www/cyberspace/webclient


Updating public and webclient files while the server is running
---------------------------------------------------------------
On Windows and Linux, whenever a file is changed in the public files dir or the webclient files dir, all public and webclient files will be reloaded from disk.
This is done via file-system watching.  This is not implemented on Mac yet.
On linux, files added in a subdirectory will not be noticed, to work around this, change one of the existing files.

When running in dev mode (--enable_dev_mode), files in the webclient files dir will be reloaded from disk freshly on each request.


Screenshot dir
--------------
This directory holds upload screenshots from the screenshot bot.

On Windows, Mac:				server_state_dir + "/screenshot_dir"
On Linux:						/var/www/cyberspace/screenshots


Server TLS keypair
------------------
On Windows and Mac, the certificate is read from 
	
	server_state_dir + "/MyCertificate.crt"

and the private key is read from 
	
	server_state_dir + "/MyKey.key"

You can generate such a keypair using OpenSSL / LibreSSL like so:

	openssl req -new -newkey rsa:4096 -x509 -sha256 -days 3650 -nodes -out MyCertificate.crt -keyout MyKey.key



Server Credentials
------------------
Server credentials are stored at
	
On Windows, Mac:				server_state_dir + "/substrata_server_credentials.txt"
Linux:							"/home/" + username + "/substrata_server_credentials.txt"			[Will change]

This contains stuff like

	email_sending_smtp_servername

for sending password reset emails etc.

The Substrata server can run without the server credentials file present, however some features will not work, such as sending password reset emails.
