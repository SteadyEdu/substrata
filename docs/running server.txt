
Notes for running the Substrata server for development
======================================================


server_state_dir is:
On Windows: APPDATA/Substrata/server_data 
On Mac: /Users/USERNAME/cyberspace_server_state
On Linux: /home/USERNAME/cyberspace_server_state

Where USERNAME is the current user name

Resources (models, textures etc. uploaded by users) are saved in server_state_dir + "/resources"

The server state database file is located at server_state_dir + "/server_state.bin"


Server Configuration file
-------------------------
If a file is present at server_state_dir + "/substrata_server_config.xml", then it will be parsed.  It should be an XML file like so:

<?xml version="1.0" encoding="utf-8"?>
<config>
	<webserver_public_files_dir>Q:\substrata\trunk\webserver_public_files</webserver_public_files_dir>
	<webclient_dir>Q:\substrata\trunk\webclient</webclient_dir>
</config>

If webclient_dir is present, then it overrides the default value of the webclient files dir specified below.
Likewise for webserver_public_files_dir.


AI models
---------
Chatbots think with an AI model.  A bot with no model of its own uses the one named by <AI_model_id>; otherwise it
uses the model chosen for it on its page in the web interface.

The models on offer are the ones built in to glare-core plus any listed in an optional <ai_models> section of the
server config.  A listed model whose <id> matches a built-in one replaces it.  This is how you point a bot at a model
running on your own network, which matters when the content should not leave the building, or when you want a model
fine-tuned for a particular grade or subject.

	<ai_models>
		<model>
			<id>local/llama-3.1-8b-instruct</id>       <!-- Stored on each chatbot.  Keep it stable. -->
			<name>Llama 3.1 8B (local)</name>          <!-- Shown when choosing a model.  Defaults to <id>. -->
			<description>Runs in the building.</description>
			<api_id>llama3.1:8b</api_id>               <!-- The id the API itself expects.  Defaults to <id>. -->
			<scheme>http</scheme>                      <!-- "https" (default) or "http". -->
			<domain>localhost</domain>
			<port>11434</port>                         <!-- Omit for the default port for the scheme. -->
			<path>/v1/chat/completions</path>
			<provider>other</provider>                 <!-- anthropic | xai | openai | google | other -->
			<reasoning_effort>none</reasoning_effort>  <!-- none | low (default) | med | high | xhigh | max -->
		</model>
	</ai_models>

<provider> selects the request format.  "anthropic" uses the Anthropic Messages API; every other value uses the
OpenAI-compatible chat completions format, which is what Ollama, llama.cpp, vLLM and LM Studio all serve.

Omit <credential_name> for an endpoint that needs no API key, which is the usual case for a locally hosted model.
Otherwise set it to the name of the entry in the server credentials file holding the key, e.g. anthropic_api_key.


Running a chatbot on a small local model
----------------------------------------
Three things will otherwise make a small local model look broken rather than merely limited.  All three were seen
with qwen3.5:2b served by Ollama.

1. Set <reasoning_effort>none</reasoning_effort>.  A small reasoning model given the chatbot system prompt can spend
   its whole output budget thinking, get truncated before it writes any content, and return an empty response.  At
   the default "low" effort that model did not answer within four minutes; at "none" it answered in about six
   seconds.  This is by far the most important setting.

2. Turn off "Allow gesture tools" on the chatbot page.  Small models tend to answer with a tool call *instead of*
   speaking, so the bot waves at the user and says nothing.

3. Use 127.0.0.1 rather than localhost in <domain> if the model server is IPv4-only, as Ollama is by default.
   "localhost" can resolve to ::1 and the connection then fails.

scripts/chatbot_test_client.py exercises all of this without needing the 3D client: it connects, logs in, stands in
front of a bot, says something and prints the replies, noting which arrived privately.


Webserver public files dir
--------------------------
This directory holds files used by the website, such as CSS files, images, javascript files (map.js) etc.
Default value:

On Windows:		server_state_dir + "/webserver_public_files"
On Mac:			server_state_dir + "/webserver_public_files"
On Linux:		/var/www/cyberspace/public_html


Webclient files dir
-------------------
This directory holds files used for the webclient, such as webclient.js, client.html etc.
Default value:

On Windows:		server_state_dir + "/webclient"
On Mac:			server_state_dir + "/webclient"
On Linux:		/var/www/cyberspace/webclient


Updating public and webclient files while the server is running
---------------------------------------------------------------
On Windows and Linux, whenever a file is changed in the public files dir or the webclient files dir, all public and webclient files will be reloaded from disk.
This is done via file-system watching.  This is not implemented on Mac yet.
On linux, files added in a subdirectory will not be noticed, to work around this, change one of the existing files.

When running in dev mode (--enable_dev_mode), files in the webclient files dir will be reloaded from disk freshly on each request.


Screenshot dir
--------------
This directory holds upload screenshots from the screenshot bot.

On Windows, Mac:				server_state_dir + "/screenshot_dir"
On Linux:						/var/www/cyberspace/screenshots


Server TLS keypair
------------------
On Windows and Mac, the certificate is read from 
	
	server_state_dir + "/MyCertificate.crt"

and the private key is read from 
	
	server_state_dir + "/MyKey.key"

You can generate such a keypair using OpenSSL / LibreSSL like so:

	openssl req -new -newkey rsa:4096 -x509 -sha256 -days 3650 -nodes -out MyCertificate.crt -keyout MyKey.key



Server Credentials
------------------
Server credentials are stored at
	
On Windows, Mac:				server_state_dir + "/substrata_server_credentials.txt"
Linux:							"/home/" + username + "/substrata_server_credentials.txt"			[Will change]

This contains stuff like

	email_sending_smtp_servername

for sending password reset emails etc.

The Substrata server can run without the server credentials file present, however some features will not work, such as sending password reset emails.
